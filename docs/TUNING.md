# Evaluation tuning

This document records the offline tuning pipeline, the dataset it ran on, the
parameter sets it produced, and the matches that decided **not** to ship them.
The short version: the pipeline works and is reproducible, three candidate sets
were produced and measured, and all three were equal or worse than the dev2
evaluation that StockBear already had. `v0.1.0-dev3` therefore ships the dev2
values, and the negative result is recorded here rather than hidden behind a
lower tuning loss.

## Why the evaluation is tunable

`src/evaluation/eval_params.cpp` holds every number the evaluation uses in one
table of 32 parameters (material, piece-square terms, pawn structure, mobility,
rook files, pawn shield, king danger), each with a middle-game and an endgame
value and an explicit legal range. The evaluation is linear in those parameters,
tapered by phase:

    score = clamp( (Σ mg_i·count_mg_i·phase + Σ eg_i·count_eg_i·(24-phase)) / 24 )

`stockbear evaldata` prints the per-parameter counts (White minus Black) for a
list of FENs, so a candidate parameter vector can be scored without a search and
without recompiling:

    score(w) = z_row · w

That linearity is what makes tuning a regression problem instead of a
search-in-the-loop problem: a whole dataset is one matrix multiply, and the
optimiser cannot drift out of sync with the engine, because the engine itself
produces the design matrix. `stockbear evaldata --check` verifies that the counts
reproduce `evaluate()` exactly, including under perturbed parameters.

## Method

* **Model.** Texel-style logistic loss, `p = 1 / (1 + 10^(-s/K))`, target 1 for
  a win, 0.5 for a draw, 0 for a loss, from the point of view of the side to
  move (converted to White's point of view for the fit, because the counts are
  White minus Black).
* **Scale `K`.** Chosen on the *training* split from a fixed candidate list
  (200…700). `K` is a tuner hyper-parameter; the engine never uses it.
* **Optimiser.** Coordinate descent over integer values, with exponentially
  shrinking steps (64 → 1) and acceptance only on a strict improvement of
  `loss + ridge·Σ((w−w0)/span)²`.
* **Regularisation.** `ridge` pulls every parameter towards its shipped value in
  units of its legal range, and `--max-delta-fraction` caps how far a single
  sweep may walk away from it. Both exist because the loss is flat along
  "pawn value versus everything else" and along "doubled-pawn penalty versus
  passed-pawn bonus": without them the fit trades one parameter for another.
* **Sign preservation.** A parameter whose shipped value is a bonus may not
  become a penalty and vice versa (`--no-preserve-sign` disables this).
* **Anchoring.** `MaterialPawn` stays at 100: absolute scale is not identifiable
  from game results alone, only relative values are.
* **Split.** Training and holdout are split **by game**, not by position. Every
  position of a game carries that game's result, so a position-level split leaks
  the label and flatters the holdout.
* **The objective is a hypothesis.** A lower tuning loss is not evidence of
  strength; only the matches below count.

forced lines.

## Candidate sets

All three candidates come from the same dataset, seed and split (80 % / 20 % by
game: 1 498 / 374 games, 60 651 / 14 765 positions). Files:
`benchmarks/results/0.1.0-dev3/tuning/variant{A,B,C}.txt`.

| set | flags | changed | holdout loss (baseline → tuned) | ship? |
| --- | --- | --- | --- | --- |
| baseline (dev2, shipped) | — | — | 0.5544 | **yes** |
| A | `--ridge 0.02 --max-delta-fraction 0.35 --no-preserve-sign` | 22 | 0.5603 → 0.5320 | no |
| B | `--ridge 0.10 --max-delta-fraction 0.20` | 7 | 0.5544 → 0.5470 | no |
| C | `--ridge 0.04 --max-delta-fraction 0.30` | 13 | 0.5544 → 0.5411 | no |

The baseline loss differs between A and B/C because `K` is picked on the training
split for each set (A: 450, B and C: 600), and each row reports the loss at its
own `K`.

Every candidate lowered the holdout loss. A lowered it the most, and it is also
the one whose parameters are least believable: it wants pawns worth 50 (the table
minimum), knights 248, and an isolated-pawn *bonus* of +9 in the middlegame. That
is the classic signature of a flat loss surface, not a discovery — exactly the
case the release criteria exist for.

## Matches

Identical engine binary, identical search; only the parameter set differs, so
each match isolates the evaluation. Controls: `--nodes 4000` (deterministic, no
clock artefacts), `--max-plies 200`, 30 openings, paired colour-reversed games,
Hash 16 MB, 1 thread, `scripts/tournament.py` pentanomial statistics. Positive
Elo always means "engine A (the shipped evaluation) was stronger".

| match | decided games | engine A score | candidate Elo, pentanomial | candidate Elo, opening-clustered | verdict |
| --- | --- | --- | --- | --- | --- |
| baseline vs candidate A | 591 | 0.6649, W/D/L 328/136/127 | **−119.1 [−140.8, −98.2]** | **−119.1 [−195.9, −52.1]** | worse, by both intervals |
| baseline vs candidate B | 590 | 0.5733, W/D/L 249/187/154 | **−51.3 [−72.1, −30.8]** | **−51.3 [−122.4, +15.7]** | no improvement; the worse reading is not confirmed |
| baseline vs candidate C | 590 | 0.4828, W/D/L 202/176/212 | **+12.0 [−10.3, +34.4]** | **+12.0 [−61.4, +86.4]** | cannot distinguish |

Both intervals are reported because they answer different questions: the
pentanomial one treats the 295 opening pairs as independent, the clustered one
knows that each opening is replayed and is therefore much wider. Only candidate
A is separated from the baseline by both. For B and C the honest statement is
"no improvement was demonstrated", not "the candidate is worse", and no candidate
was shipped in either case.

### The check that the ablation really is an ablation

Because the shipped set and the dev2 baseline are the same values in dev3, the
control is worth measuring explicitly. Same binary on both sides, engine B given
`--b-option EvalParams=benchmarks/params/dev2-baseline.txt` (the file that is
byte-identical to the compiled table), 200 games, seed `20261108`:

| decided | W/D/L | score | opening pairs | unadj. |
| --- | --- | --- | --- | --- |
| 200 | 70/60/70 | 0.5000 | 100 of 100 pairs split one win each | 0 |

As expected for two identical evaluations, no pair separated: a zero-Elo result
with no variance information, not a "proof of equality". If a future release
changes the shipped set, this same command becomes a real match. Raw record:
`benchmarks/results/0.1.0-dev3/match-dev2-shipped-regression.jsonl`.

Pentanomial counts (0 / 0.5 / 1 / 1.5 / 2 pairs) are in
`benchmarks/results/0.1.0-dev3/tuning/match-eval-{A,B,C}.jsonl`. Games that
reached the ply cap are recorded as unadjudicated (9, 10 and 10 respectively) and
were never converted into draws.

Note the ordering: the set with the better holdout loss (A) is the one that lost
by the largest margin, and the set with the worst holdout loss (C) is the only
one that did not lose. The tuning objective simply does not rank these sets the
way the match does.

## Why the tuning did not produce a stronger engine

* **Self-play labels are biased towards what the engine already believes.** A
  position is labelled with the result of a game between two copies of the same
  dev2 engine. The label rewards the moves dev2 liked, so the fit is pulled
  towards reproducing dev2's choices, not towards better ones.
* **The parameter vector is not used only for scoring.** Material values are also
  the scale of the search's pruning margins (static exchange evaluation, delta
  and futility margins). Halving the material values — which is what candidate A
  and, to a lesser extent, B and C did — changes how aggressively the search
  prunes. The measured Elo difference therefore mixes "different weights" with
  "different pruning", and the pruning interaction is not necessarily an
  improvement: at depth 7 candidate A explores 345 125 nodes where the shipped set
  explores 255 021, i.e. its pruning is *less* effective at equal depth, which is
  the opposite of what the extra material scale suggests.
* **Flat, correlated directions.** Pawn, sergeant/knight/rook values trade off
  against each other, and pawn-structure terms trade off against material. With
  15 000 holdout positions the holdout cannot separate them; the ridge is what
  keeps the fit from wandering, and the ridge is a guess.

A future attempt should (a) train on positions with *engine-independent* labels
(curated tactics and endgames, or another engine's analysis under a licence that
permits it), (b) separate the pruning scale from the evaluation scale, and
(c) validate on a time control rather than only on equal node counts.

## Reproducing a run

```bash
# 1. self-play games (deterministic node budget per move)
python3 scripts/tournament.py --engine-a bin/stockbear-dev2 --engine-b bin/stockbear-dev2 \
    --games 2000 --nodes 6000 --max-plies 180 --seed 20261101 \
    --pgn benchmarks/tuning/selfplay.pgn --jsonl /tmp/selfplay.jsonl

# 2. dataset
python3 scripts/build_tuning_data.py --pgn benchmarks/tuning/selfplay.pgn \
    --out /tmp/positions.epd --meta /tmp/positions.meta.json

# 3. design matrix (the engine owns the feature order)
build/stockbear evaldata --input /tmp/positions.epd --output /tmp/features.csv

# 4. fit
python3 scripts/tune_eval.py --features /tmp/features.csv --meta /tmp/positions.meta.json \
    --engine build/stockbear --out /tmp/tuned.txt --report /tmp/tuning.json \
    --sweeps 80 --tune-k --ridge 0.04 --max-delta-fraction 0.30

# 5. measure (same binary on both sides; only the parameter file differs)
python3 scripts/tournament.py --engine-a build/stockbear --engine-b build/stockbear \
    --b-option EvalParams=/tmp/tuned.txt --games 600 --nodes 4000 --max-plies 200 \
    --seed 20261103 --pgn /tmp/match.pgn --jsonl /tmp/match.jsonl
```

`setoption name EvalParams value <file>` installs a parameter set at run time;
sending it with an empty value restores the shipped set. It clears the
transposition table, because stored scores from a different evaluation are not
comparable.

## What ships

`benchmarks/params/dev3-shipped.txt` is the released evaluation and is identical
to `benchmarks/params/dev2-baseline.txt`: the dev2 values, checksum
`da1921f604ae255e`. `tests/unit/test_eval_baseline.cpp` proves on benchmark and
randomly generated positions that the parameterised dev3 evaluation reproduces an
independent re-implementation of the dev2 formulae exactly, and checks that the
parameter file in the repository still matches the compiled table.

## Known limitations

* The tuning data is self-play of one engine at one node budget on 30 openings.
* The holdout is 374 games / 14 765 positions: enough to reject candidate A's
  excursions, not enough to resolve a 10 Elo difference.
* Material scale is anchored by hand (pawn = 100) and the ridge keeps candidates
  within a fraction of their ranges; that is a deliberate trade of possible Elo
  for a set a reviewer can still read.
* No endgame tablebases are used, so endgame parameters are fitted from a small
  number of simplified self-play positions.
