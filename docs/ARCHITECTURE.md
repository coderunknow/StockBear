# Architecture and implementation boundaries

## Chess core

`Position` maintains a mailbox, per-color and per-piece bitboards, side to move, castling rights, FEN en-passant square, clocks, material/positional accumulators and an owned vector of per-ply states. Moves incrementally update them; unmake restores the captured piece from the state being popped and restores the previous key, counters and accumulators exactly. There are no pointers into the state vector. Castling rights are updated for king/rook moves and rook captures on home squares.

Leaper attacks are precomputed; sliding attacks use multiplication-indexed bitboards. The multipliers are generated by our deterministic `tools/gen_magics.cpp`, not imported from another engine. Initialization checks every occupancy subset for destructive collisions. Tests also compare the tables with a separate ray walker. Legal generation handles pins and check evasions without allowing king captures; king moves use occupancy with the king removed. En passant uses the full post-capture occupancy, including removal of the captured pawn, for king safety. Castling tests empty paths and king transit attacks.

FEN parsing is transactional and checks six fields, board shape, kings, pawn back ranks, side, counters, rights and en-passant consistency. It rejects adjacent kings and a side-not-to-move king left in check. This is structural/rule validation, **not proof of a reachable game history**. FEN counters above 10^12 are rejected. FEN preserves a raw double-push target even if no capture exists.

A fixed-seed Zobrist hash covers pieces, turn, castling rights and an en-passant file **only if a legal capture is available**. A stored FEN starts a new known history; passing moves with UCI `position ... moves ...` records subsequent history. Position equivalence for repetition uses that hash. The core distinguishes current/intended-move threefold and fifty-move claims from fivefold and 75-move automatic draws, checkmate, and stalemate. The material-only dead-position detector handles bare kings, one minor, and bishops-only positions where all bishops occupy the same square color; it does not solve every FIDE dead position involving locked material. The UCI interface cannot itself claim a draw, so a GUI/referee must adjudicate it.

## Search and evaluation

One worker performs iterative deepening over negamax alpha-beta with principal variation search, quiescence (all evasions in check; captures and all promotion choices otherwise), MVV-LVA-style capture ordering, killer moves, history ordering and up to two check extensions on a path. There is no null-move pruning, LMR, aspiration window, tablebase or parallel search. Mate scores are distance-normalized when stored in the transposition table. The table is bounded by the Hash setting and protected from incompatible reversible histories, fifty-move clocks, search-root history boundaries and check-extension budgets; this conservative context reduces cross-path hits. Zobrist collisions remain theoretically possible.

Search scores are from the side-to-move perspective. Search assumes that current claimable draws are taken; a repeated position inside the search tree is treated as a draw to break cycles. That is a search heuristic, not a declaration that a twofold position is a FIDE draw. Terminal mate is checked before a move-count draw. An interrupted search retains the last complete iteration's best move or a legal root fallback. Depth/node/time bounds can be combined; node limits are hard caps. Time management reserves a small communication allowance and uses a soft and hard budget for clocks. It does not predict future opponent speed or network latency.

Evaluation is independently written, handcrafted and non-neural. It combines material and formula-derived piece-square values with tapered middlegame/endgame weights, pawn isolation/doubling/passed-pawn features, bishop pair, mobility, rook files, pawn shelter and king-zone attacks. The numbers are initial heuristics, not trained or tuned weights. The evaluation is clamped below mate scores.

## Protocol and concurrency

The main thread reads UCI and serializes output. A single search worker owns a position copy. `stop` is an atomic flag; position changes, Hash changes, new games and quit join the worker before changing shared state. `isready` does not stop it. Tables are initialized once; TT access is confined to the joined worker. No stdout diagnostics are emitted outside UCI `info string`/protocol responses.

## Deliberate limits

- Standard chess only; no Chess960, pondering, `searchmoves`, MultiPV, opening book or tablebases.
- No NNUE/transformer/policy network, training, MCTS or GPU inference. These are research directions, not hidden implementations.
- Very long paths can reach the explicit `MAX_PLY` search safety horizon; the engine returns a heuristic score there.
- Insufficient material is a recognized subset of all possible FIDE dead positions; no arbitrary-position retrograde proof is attempted.
- Repetition prior to the supplied FEN is unknowable; supply the game move sequence where possible.
- Clock management and evaluation are baseline heuristics. No statistically reliable Elo claim follows from the small included match.

## Research-only reachability

A bounded exact-identity movement-graph probe exists in `chess/dead_position.*` for testing. It is not used in search or adjudication and is not a complete FIDE solver. See [the investigation](DEAD_POSITION_RESEARCH.md).
