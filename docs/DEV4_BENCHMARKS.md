# StockBear dev4 — benchmarking method and results

This document describes how dev4's candidates were measured, why the previous
release's match methodology turned out to be unable to resolve small effects, and
what every experiment actually returned.

## 1. The measurement problem dev4 had to fix

dev3 measured candidates with paired colour-reversed matches at a **fixed node
budget**. Play at a fixed node budget is deterministic: given the same opening,
the same engine and the same node limit, every move is a pure function of the
position. The two games of a colour-reversed pair are therefore *exact mirrors*
of each other, always scoring 1.0, and the pentanomial has **zero variance**.

dev4 found this the hard way. A 60-game control match of the dev4 binary against
itself produced `pair scores 2/1.5/1/0.5/0 = [0, 0, 30, 0, 0]` — every single
pair at exactly 1.0, score 0.500, and the statistics layer correctly refused to
report an interval ("all pairs scored identically"). A match that always returns
1.0 per pair cannot distinguish a +100 Elo change from a −100 Elo one.

Two changes fixed it:

1. **Seeded per-move node jitter** (`--nodes-jitter F`): each move's node budget
   is drawn uniformly from `[N(1−F), N(1+F)]`, from a generator seeded by the
   game index. The match stays reproducible from `--seed`, but the two games of a
   pair are no longer identical, so the pentanomial has real variance. All dev4
   fixed-node experiments use `F = 0.12`.
2. **A larger opening suite** (`benchmarks/positions/openings_dev4.txt`, 240
   lines, generated by `scripts/make_openings.py --count 240 --plies 8
   --seed 20261101`). With 31 openings, a 240-game match plays each opening eight
   times; with 240 openings each is played once per colour pair, so the clustered
   interval has 120 independent clusters instead of 15.

## 2. Protocol

* **Paired, colour-reversed**, both games of a pair from the same opening.
* **Two statistics**, both reported:
  * pentanomial model over opening pairs (normal interval on the pair mean);
  * **opening-clustered (CR1)** variance with a Student-t interval on `G−1`
    degrees of freedom. The clustered interval is the one quoted in this
    document's tables, because it does not assume that openings contribute
    equally.
* **A null-control match for every condition.** Two identical builds, same
  options, same time control, played through the same harness. Whatever the
  control reports is the harness's own noise/bias, and no candidate is called an
  improvement without being at least clearly better than that.
* **Fixed nodes and fixed time.** Pruning and reduction changes must be measured
  at the *node* budget they were designed for (they change how much work a node
  buys), but anything that changes the cost of a node must also be measured at a
  fixed *time* control, because that is what a player feels. dev4 runs both.
* **Nothing is claimed without an interval.** A candidate whose interval includes
  zero is reported as "no measurable effect", not as a win.

## 3. Conditions

| Item | Value |
| --- | --- |
| Machine | 2 vCPU (1 physical core), 3 GB RAM, Debian 12, GCC 12.2.0, `-O3`, no `-march=native` |
| Fixed node condition | 3,000 nodes/move, ±12 % jitter, hash 16 MB, 1 thread |
| Fixed time condition | 40 ms + 4 ms increment, hash 16 MB, 1 thread |
| Adjudication | python-chess; checkmate, stalemate, repetition, 50-move, insufficient material; 240-ply cap; no resign/time adjudication other than a real clock loss |
| Openings | `benchmarks/positions/openings_dev4.txt` (240 random 8-ply openings) |
| Seed | 20261031 (opening shuffle), per-game jitter seed derived from the game index |

## 4. Results

Every row is copied from `benchmarks/results/0.1.0-dev4/experiments/summary.csv`,
which `scripts/experiment_table.py` regenerates from the raw JSONL records.

### 4.1 Regression gate: dev3 versus dev4

| Experiment | Games | Score (dev4) | Elo (dev4 − dev3) | 95 % CI (clustered) |
| --- | --- | --- | --- | --- |
| fixed nodes 3,000 | 398 | 0.4823 | −12.3 | [−34.2, +9.5] |
| fixed time 40+4 ms | 240 | 0.5417 | +29.0 (dev4 ahead) | [+1.5, +56.9] |

The dev4 default configuration is dev3's configuration: every new feature is off
by default, and the depth-6/depth-7 benchmark signatures are unchanged
(`e06c4352681ae8eb`, `5bceff035f2a4ae4`). The fixed-node match is therefore a
null test, and it reproduced the *identical* per-game records as the
same-binary null control — bit-identical play, as expected.

**The fixed-time row is the interesting one, and it is not a result.** It reports
+29 Elo for dev4 with a lower bound above zero — which would be a "meaningful"
gain if taken at face value. It must not be: the same binary against itself in
this condition scored −30.5 [−65.9, +4.3] (row 4.2), the two builds have
identical node counts at depth 6 and 7 (105,743 / 87,419), and identical bench
throughput within measurement noise (2.58 vs 2.63 Mnps at depth 6, 2.69 vs
2.65 Mnps at depth 7). Nothing in the binaries can produce a 60 Elo swing at a
40 ms time control; the swing is the harness's own scheduling noise, which is why
every candidate in §4.3 was required to beat the null control rather than merely
to exclude zero. **Verdict: no measurable difference between dev3 and dev4 at
either condition.**

### 4.2 Null controls (the harness's own noise floor)

| Experiment | Games | Score | Elo (A − B, A and B identical) | 95 % CI |
| --- | --- | --- | --- | --- |
| fixed nodes 3,000 | 398 | 0.4823 | −12.3 | [−34.2, +9.5] |
| fixed time 40+4 ms | 160 | 0.4562 | −30.5 | [−65.9, +4.3] |

Both controls are consistent with zero, but they are not small: a single
fixed-time match can land anywhere in a ~±30 Elo band around the truth, and it
can also *exclude zero* while doing so (the dev3-vs-dev4 fixed-time row above).
The fixed-node control is tighter (−12.3 [−34.2, +9.5]) because the only source
of variance there is the seeded node jitter, not the scheduler. **Any single
fixed-time result in this document smaller than about 65 Elo is not
distinguishable from harness noise, whatever its interval says.**

### 4.3 Search candidates

Each candidate was measured against the same binary with that single option
turned off, so the only difference is the candidate itself.

| Candidate | Fixed nodes 3,000 (400 games) | Fixed time 40+4 ms (160 games) | Verdict |
| --- | --- | --- | --- |
| `ModernLMR` | −28.7 [−52.0, −5.7] | −30.9 [−69.0, +6.5] | **Rejected** (negative at fixed nodes) |
| `MoveCountPruning` | −39.3 [−67.9, −11.1] | −104.2 [−154.6, −57.7] | **Rejected** (clearly negative in both) |
| `IIR` | −14.9 [−37.3, +7.4] | +6.6 [−32.2, +45.5] | **Rejected** (no measurable effect) |
| `Improving` | −26.4 [−49.3, −3.7] | −13.0 [−44.6, +18.3] | **Rejected** (negative at fixed nodes) |

Node counts at depth 6 explain the pattern:

| Configuration | Bench nodes (depth 6) | Relative |
| --- | --- | --- |
| dev3 default | 105,743 | 1.00 |
| `ModernLMR` | 139,989 | 1.32 |
| `MoveCountPruning` | 20,915 | 0.20 |
| `IIR` | 103,310 | 0.98 |
| `Improving` | 97,287 | 0.92 |
| `TTEval` | 105,743 | 1.00 |

* `ModernLMR` **increases** the tree by a third: its schedule reduces less than
  dev3's existing reduction schedule, so it is a weakening, not a modernisation.
* `MoveCountPruning` cuts the tree to a fifth, and loses badly in both
  conditions: at `3 + depth²` quiet moves the limit is far more aggressive than
  this engine's move ordering can support — it prunes moves that matter.
* `IIR` barely changes the tree (a 2 % saving), which is why it cannot move the
  needle either way.
* `TTEval` changes neither the tree nor the result, because with a fresh table
  per position the stored evaluation equals the computed one.

The consistent message is that dev3's search is already at a local optimum for
its evaluation and node budget: every "standard" modern addition tested here is
neutral or harmful.

### 4.4 Learned evaluation

| Experiment | Games | Score | Elo (NNUE − classical) | 95 % CI |
| --- | --- | --- | --- | --- |
| NNUE (128×32, 3.07 M positions) vs classical, fixed nodes 2,500 | 60 | 0.0167 | **−708** | **[−1011, −405]** |
| Control: NNUE on both sides | 40 | 0.5875 | +61 | [−28, +160] |

The network loses 58 of 60 games. The control shows the engine is not broken with
the network loaded — it plays self-consistent games — so the result is an honest
statement about evaluator quality, not about a crash or an illegal-move bug. The
detail is in `DEV4_TRAINING.md` §6.

## 5. Performance

| Item | Value |
| --- | --- |
| Search throughput, classical evaluation | 0.543 µs/node (depth-7 bench) |
| Search throughput, neural evaluation | 0.735 µs/node (same bench) |
| Neural evaluation cost | ~35 % more per node at 128×32 |
| Bench, depth 6, default configuration | 105,743 nodes, 42.4 ms (2.49 Mnps) |
| Bench, depth 7, default configuration | 87,419 nodes, 47.5 ms (1.84 Mnps) |
| Binary size, Linux x64, release | see the release assets table in the report |

The neural evaluation's cost is a real part of why it is not shipped: at a fixed
time control it would start 35 % behind before any question of quality.

## 6. What these measurements do **not** show

* They do not show that the candidates would fail at a long time control. The
  fixed-time condition here is 40 ms/move, which is very fast; a 1 s/move
  condition would need ~10× the wall clock per game and was not affordable on one
  core within the project's compute budget. This is a limitation, not a result.
* They do not show that the search cannot be improved — only that these four
  candidates, implemented this way, do not improve it.
* They do not establish a confidence interval narrower than about ±35 Elo at
  fixed nodes and ±65 Elo at fixed time for a single experiment. Effects below
  that size would need several thousand games per candidate.

## 7. Reproducing a row

```sh
cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release
cmake --build build-release --parallel 2

# fixed nodes
python3 scripts/tournament.py \
  --engine-a build-release/stockbear --engine-b /path/to/dev3/stockbear \
  --games 400 --nodes 3000 --nodes-jitter 0.12 --hash 16 --threads 1 \
  --max-plies 240 --openings benchmarks/positions/openings_dev4.txt \
  --jsonl match.jsonl --pgn match.pgn

# regenerate the table from the recorded matches
python3 scripts/experiment_table.py benchmarks/results/0.1.0-dev4/experiments/*.jsonl
```

`--a-option NAME=true --b-option NAME=false` runs an in-binary ablation, which is
how §4.3 was measured: the control arm is the same binary, so a build difference
cannot be mistaken for a feature effect.
