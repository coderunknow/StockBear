# StockBear dev4 — architecture

This document describes how dev4 is put together: what the new modules are, how
data flows between them, and which invariants each one has to preserve. It is
written for someone who has to change the code later, so it concentrates on the
places where a change is *safe* and the places where a change breaks something
silently.

## 1. Overview

dev4 adds a learned evaluation to an otherwise unchanged engine. Nothing in the
search, the move generator or the protocol layer had to be restructured: the
evaluation is a drop-in replacement for `evaluate(Position)`, and the classical
implementation remains in the binary as the fallback and as the control arm of
every experiment.

```
                    +-------------------------------+
  UCI  ------------>| uci.cpp                       |
                    |  options: NNUE, NnueFile,     |
                    |           ModernLMR, IIR, ... |
                    +---------------+---------------+
                                    |
                    +---------------v---------------+
                    | search.cpp                    |
                    |  PVS + quiescence             |
                    |  evaluate(pos)  <-------------+--- evaluation.cpp
                    +---------------+---------------+        |
                                    |                        | classical
                    +---------------v---------------+        | (32 tapered
                    | nnue.cpp                      |        |  params)
                    |  accumulator refresh / delta  |        |
                    +---------------+---------------+        |
                                    |                        |
                    +---------------v---------------+        |
                    | nnue_forward.cpp (scalar)     |        |
                    | nnue_forward_avx2.cpp (AVX2)  |        |
                    +---------------+---------------+        |
                                    |                        |
                    +---------------v---------------+        |
                    | nnue_net_data.cpp (embedded)  |        |
                    |   or NnueFile on disk         |        |
                    +-------------------------------+--------+
```

## 2. New modules

| File | Responsibility |
| --- | --- |
| `src/evaluation/nnue.hpp` | `Network`, `Accumulator`, the serialisation contract, the public API (install/clear/active network, feature extraction, incremental updates, evaluation) |
| `src/evaluation/nnue.cpp` | format parsing with full validation, checksum, accumulator refresh/delta, `evaluate()` and the perspective ordering |
| `src/evaluation/nnue_forward.hpp` | the integer forward pass contract and kernel selection |
| `src/evaluation/nnue_forward.cpp` | portable scalar kernel, runtime kernel choice, kernel name for provenance output |
| `src/evaluation/nnue_forward_avx2.cpp` | AVX2 kernel, compiled in its own translation unit with `-mavx2`, entered only after a CPUID check |
| `src/evaluation/nnue_embedded.hpp`, `src/evaluation/nnue_net_data.cpp` | the network compiled into the binary; the `.cpp` is generated by `scripts/embed_nnue.py` and must never be edited by hand |
| `src/utilities/nnuecli.cpp` | `stockbear nnue` — feature dump, evaluation, incremental-vs-scratch comparison; the tool the Python mirror is differentially tested against |

| `scripts/nnue_features.py` | the Python mirror of the feature function |
| `scripts/train_nnue.py` | corpus preparation, game-level split, training, validation, checkpointing |
| `scripts/convert_nnue.py` | float → integer quantisation, calibration, verification, `.nnue` writer |
| `scripts/embed_nnue.py` | `.nnue` → generated C++ source |

## 3. Data flow

### 3.1 Where the accumulator lives

A position stores one accumulator per ply, in a stack parallel to the existing
`history_`:

```
class Position {
    std::vector<StateInfo> history_;      // keys, material/PSQT accumulators, ...
    std::vector<nnue::Accumulator> nnueStack_;   // same length
};
```

`Accumulator` is `int16_t v[2][MaxL1]` — two perspectives, `MaxL1 = 256` — so
one accumulator is at most 1 KB and a full 246-ply stack is at most ~250 KB per
position. The stack is separate from `StateInfo` on purpose: `StateInfo` is
copied on every `make_move` for the repetition/king-safety bookkeeping, and
copying half a kilobyte per node would cost more than the evaluation saves.

### 3.2 Incremental maintenance

The invariant is: **`nnueStack_.back()` is exactly `refresh(position)`**. It is
maintained in four places and nowhere else:

| Operation | Action |
| --- | --- |
| `make_move_impl` | copy the top accumulator, then for each of (captured piece, from-square, to-square, promotion piece, castling rook) apply `add_piece`/`subtract_piece` |
| `unmake_move` | pop the stack (the previous entry is already correct) |
| `make_null_move` / `unmake_null_move` | push a copy / pop, because the placement does not change |
| `Position::set` (FEN) | `refresh_nnue_accumulator()` rebuilds the whole stack |

With a single king bucket the delta depends only on (piece, square,
perspective), which is what makes the incremental update a pure function and
lets `verify_state()` recompute from scratch and compare — see below.

`Position::verify_state()` rebuilds the accumulator and compares it against the
incremental one. Every unit test that makes a move calls it, which turns a whole
class of silent evaluation corruption (a missed en-passant subtraction, a
promotion that forgets to remove the pawn) into a test failure.

### 3.3 The ordering contract

The network input is `[side to move, opponent]`, and every kernel obeys it:
`evaluate()` passes `acc.v[me]` then `acc.v[me ^ 1]`. This is the single most
important invariant in the module, because violating it does not crash, does not
change node counts, and does not fail any structural test — it just makes the
network unable to learn (`DEV4_TRAINING.md` §3). `test_nnue.cpp` pins it by
constructing the expected forward value from the two accumulator halves and
checking that the swapped call differs.

### 3.4 Forward pass

```
acc[p][i]        int16      sum of active feature weights + bias
a[i]  = clip(acc >> actShift, 0, 127)              (Q7 activation)
h[j]  = clip((W2 · a)[j] + b2[j] >> h2Shift, 0, 127)
out   = (W3 · h) + b3                              int32
cp    = out >> outShift                            (centipawns)
```

`actShift`, `h2Shift` and `outShift` are properties of the file, so a
retrained network can rescale itself without an engine change. `evaluate()`
clamps to `±VALUE_KNOWN_WIN` so the search never sees a neural score in mate
range.

Two kernels implement this:

* `forward_scalar` — portable, auto-vectorisable, always available.
* `forward_avx2` — `_mm256_madd_epi16` over the layer-2 dot product; compiled
  with `-mavx2` in its own translation unit and only called when
  `cpu_has_avx2()` (CPUID + XGETBV) says the CPU and OS support it.

They must be bit-identical, and `test_nnue.cpp` checks that on several
positions. The selected kernel name is printed by `bench` and by
`stockbear nnue --info`, so a release's performance claim can be attributed to a
specific code path.

### 3.5 Network lifecycle

`install_network` takes a copy and validates it; `clear_network` releases it.
The active network is a process-wide `unique_ptr<Network>` behind a mutex-free
accessor (installation happens before any search starts). Every accessor
tolerates `nullptr`: with no network active, `evaluate()` is the classical
function, `refresh`/`add_piece` are no-ops, and `nnuecli` says so.

Two ways to install one:

* **embedded** — installed by the `Uci` constructor before the start position is
  set. `src/evaluation/nnue_net_data.cpp` holds the bytes; a build with no
  trained network embeds a zero-length blob and the engine silently keeps the
  classical evaluation.
* **file** — `setoption name NnueFile value <path>`, with `NNUE` as the
  on/off check option. An empty path restores the embedded network.

Because the network is installed before any `Position` exists, `nnueStack_` is
correct from the first position, and a later install forces a
`refresh_nnue_accumulator()` on the current position so the accumulator matches
the new weights.

## 4. File format

All values little-endian, so a network trained on one platform loads on every
other one:

```
offset  size  field
0       4     magic "SBNN"
4       2     version (1)
6       2     kingBuckets   (1 = 768 plain piece-square features)
8       2     l1
10      2     l2
12      2     actShift
14      2     h2Shift
16      2     outShift
18      2     reserved
20      ...   i16 w1[inputCount * l1]   feature-major
        ...   i32 b1[l1]
        ...   i16 w2[l2 * 2 * l1]        side-to-move rows first
        ...   i32 b2[l2]
        ...   i16 w3[l2]
        ...   i32 b3
```

The loader rejects a wrong magic, an unknown version, dimensions outside
`MaxBuckets/MaxL1/MaxL2`, a byte count that does not match the dimensions, and
a network whose worst-case accumulator could overflow int16
(`maxWeight*32 + maxBias > 32000`). A checksum over all parameters identifies a
network in logs and in the `bench` header.

`bench --network PATH` and `--no-nnue` select the art in use so a benchmark run
can be reproduced exactly; the header line prints the network identity and the
kernel name.

## 5. Search-side additions

Five refinements, each behind its own option, all defaulting to the dev3
behaviour:

| Option | Where it lives | Effect when enabled |
| --- | --- | --- |
| `ModernLMR` | `search/lmr_table.inc`, `search.cpp` | log-log reduction table, PV/improving/killer adjustments |
| `MoveCountPruning` | `search.cpp` | skip late quiets at shallow depth |
| `IIR` | `search.cpp` | reduced internal iterative deepening when the TT has no move |
| `Improving` | `search.cpp` | per-ply static-eval stack drives RFP margin and LMP limits |
| `TTEval` | `transposition_table.{hpp,cpp}` | cache the static eval in the TT, cleared on a key mismatch |

The control arm is the same binary with the options off, which is why `bench`
prints a signature that is bit-identical to dev3's when they are off.

## 6. Determinism and resources

* The engine is single-threaded. No `Threads` option is advertised, because
  multi-threading is implemented nowhere in this codebase and advertising it
  would be a claim the binary cannot honour.
* Self-play generation is deterministic: the seed drives the opening choice and
  the per-move node jitter, and the generator uses one search object per game.
* Training is deterministic given the seed, the corpus hashes and the recorded
  hyper-parameters, all of which are stored in the checkpoint.
* Peak memory: training uses ~1.5 GB for 3M positions with the default batch
  size; the engine itself needs `hash` MB plus a few hundred KB.
